title: "Shipments"
description: "Create a shipment from an order reference and two map pins, and read it back."
---

Creating a shipment takes four fields. Everything else is either optional or derived.

## The minimal request

```bash
curl -X POST "$BASE_URL/v2/external/shipments" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
        "reference": "ORDER-1042",
        "pickup":      { "latitude": 24.7136,   "longitude": 46.6753 },
        "destination": { "latitude": 24.774265, "longitude": 46.738586 },
        "recipient":   { "name": "Noura", "mobile": "0551234567" }
      }'
```

Requires the `shipments:write` scope.

| Field | Notes |
| --- | --- |
| `reference` | Your order identifier, 1–128 characters. Also the idempotency key. |
| `pickup` | Where to collect. A coordinate pin, or a saved pickup code. |
| `destination` | Where to deliver. A coordinate pin. |
| `recipient` | `name` (1–120 characters) and `mobile`. |

<Note>
  There is no quote call to make first, no branch or pickup-location code to look up, no city or address to supply, no carrier to name, and no service level to choose. Sending more than the four fields above does not get you a better shipment — it gets you a rejected request, because the payload is closed.
</Note>

## What DropHub derives

From those two coordinates alone, DropHub resolves address and city context, the route and its distance, whether the lane is covered, the price under your commercial terms, the eligible carrier, the service and its defaults, dispatch, the lifecycle starting state, SAR as the currency with prepaid as the payment mode, and the customer tracking URL.

None of these are inputs, and none are configurable through this API.

## Phone numbers

`mobile` is a Saudi mobile number. Three shapes are accepted:

| You send | DropHub stores |
| --- | --- |
| `0551234567` | `+966551234567` |
| `551234567` | `+966551234567` |
| `+966551234567` | `+966551234567` |

Normalization happens on the way in, so you do not need to canonicalize first. Anything that is not one of these three shapes is rejected with `422`.

## Optional fields

Add these only when the default is wrong for the order.

<AccordionGroup>
  <Accordion title="Parcel — when it is not one small box">
    The default parcel is one piece, 1 kg, ambient, described as "Parcel". Override any part of it:

    ```json
    "parcel": { "description": "Small box", "pieces": 1, "weightKg": 2.4 }
    ```

    `pieces` is 1–100. `weightKg` is greater than zero. `description` is 1–160 characters.
  </Accordion>

  <Accordion title="COD — when the driver collects payment">
    ```json
    "codAmount": 125.00
    ```

    An exact decimal in SAR, greater than zero, to two places. **Omit it entirely for prepaid orders** — that is what makes an order prepaid. Sending `0` is not the way to say "no COD"; leaving the field out is.
  </Accordion>

  <Accordion title="Saved pickup — when you always collect from the same place">
    If your account has a saved pickup location, use its code instead of a coordinate:

    ```json
    "pickup": { "savedLocationCode": "MAIN" }
    ```

    `pickup` is one or the other — a `savedLocationCode`, or a `latitude`/`longitude` pair. Never both.
  </Accordion>

  <Accordion title="Pickup window — when collection is time-bound">
    ```json
    "pickupWindow": { "start": "2026-08-27T09:00:00Z", "end": "2026-08-27T12:00:00Z" }
    ```

    Both bounds are required together, in UTC. Omit the whole object to let DropHub collect as soon as it can.
  </Accordion>
</AccordionGroup>

A request using all of them:

```json
{
  "reference": "ORDER-1043",
  "pickup": { "savedLocationCode": "MAIN" },
  "destination": { "latitude": 24.774265, "longitude": 46.738586 },
  "recipient": { "name": "Noura", "mobile": "+966551234567" },
  "parcel": { "description": "Small box", "pieces": 1, "weightKg": 2.4 },
  "codAmount": 125.00,
  "pickupWindow": { "start": "2026-08-27T09:00:00Z", "end": "2026-08-27T12:00:00Z" }
}
```

## The response

Deliberately small — it carries what you cannot compute yourself and nothing more.

```json
{
  "id": "0198f7c0-7f51-7000-8000-000000000001",
  "reference": "ORDER-1042",
  "status": "CREATED",
  "trackingUrl": "/track/jhJ4hVsHM7APbKpYKg3f7w4m2fC0ZLDm7KqTKi2B1zA",
  "codAmount": null,
  "createdAt": "2026-08-27T06:00:00Z",
  "version": 1
}
```

`201` carries a `Location` header and an `ETag`. `trackingUrl` is the customer link, minted automatically — see [Tracking](/tracking).

## Retries are already safe

`reference` is the idempotency key. You do not need to send an `Idempotency-Key` header.

| Situation | Result |
| --- | --- |
| Same reference, same request | `200` with the original shipment |
| Same reference, different request | `409` — pick a new reference |
| New reference | `201` — a second shipment |

<Warning>
  Because `reference` is the key, reusing one order number for a genuinely different shipment is a conflict, not an update. One order number, one shipment.
</Warning>

The optional `Idempotency-Key` header (16–128 characters) exists for callers who already have a key of their own. An explicit key always wins over the derived one. See [Idempotency and ETags](/idempotency-and-etags).

## Read one back

```bash
curl "$BASE_URL/v2/external/shipments/$SHIPMENT_ID" \
  -H "Authorization: Bearer $ACCESS_TOKEN"
```

Requires `shipments:read`, and returns the same shape as the create response with a current `status` and `version`.

<Note>
  There is no collection endpoint and no search. Shipments are addressed by the `id` you were handed at creation — store it against your order. For progress, use [webhooks](/webhooks) rather than polling a list.
</Note>

## Status

Seven public statuses, and no others:

| Status | Meaning |
| --- | --- |
| `CREATED` | Accepted; not yet assigned to a driver |
| `ASSIGNED` | A driver is on it |
| `PICKED_UP` | Collected from the pickup point |
| `OUT_FOR_DELIVERY` | On the way to the recipient |
| `DELIVERED` | Terminal — delivered |
| `FAILED` | Terminal — delivery did not succeed |
| `CANCELLED` | Terminal — cancelled |

<Tip>
  Treat status as a value to read, not a sequence to assume. DropHub's internal dispatch states are collapsed into these seven on the way out, so a shipment may skip what looks like a step, and `FAILED` is an ordinary outcome rather than an error.
</Tip>
